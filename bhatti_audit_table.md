# Bhatti five-principle audit

## Scope and provenance

The audited API is the seven project-declared methods of `Handler` in
[server.py](server.py). The preserved [raw draft](audit/ai_docstring.py) was
generated by a Codex agent from signatures and a short goal before the agent
read the implementation. Its behavior claims were explicitly labeled assumptions
or unknowns. The code-informed revision is in `server.py`.

An independent human manual-authoring session was **not performed**. Actual
GPT-4 and Claude engines were **not called**. A file named `manual_docstring.py`,
if included elsewhere in the submission, denotes the code-informed comparison
artifact; its filename does not establish human authorship. This is an honest
Codex draft versus code-reviewed Codex revision, rather than a completed
independent human-versus-GPT-4/Claude experiment. See
[generation provenance](audit/ai_generation_provenance.md).

The [Sprint 06 lab handout](<C:/Users/PDulg/Downloads/Sprint 06 Lab Instructions - GitLab & Code Documentation.pdf>)
explicitly lists **Explained, Concise, Clear, Usable, Trustworthy** in US-6.3.
Those five labels organize this matrix. Assessments are qualitative code-review
judgments, not validated numerical measurements or peer-review results.

## Concrete correction register

The following corrections were checked against method bodies and the revised
docstrings. They exceed the handout's minimum of two corrections. They are
code-informed agent corrections, not asserted human manual corrections.

| ID | Draft hypothesis or omission | Verified correction | Source symbol |
|---|---|---|---|
| C01 | Command body contains `action` and `text`. | Exactly `session_id`, `transcript`, `intent`, `event`; intent must be `calendar.create`. The event has exactly `title`, `start`, `end`, `timezone`. | `Handler.dispatch`, `fields` |
| C02 | Confirmation contains `action` and `confirmed`; execution contains `action`. | Both bodies contain exactly `session_id`, `payload_version`. The path selects `confirm` or `execute` and identifies the action. Boolean versions are rejected because the type check requires `int` exactly. | `Handler.dispatch` |
| C03 | Envelope contains `message`. | It contains `status`, `user_message`, `correlation_id`; the last value comes from `self.correlation`. | `Handler.envelope` |
| C04 | `log_message()` writes to the default log. | The override is a no-op, accepts and ignores its arguments, and returns `None`. | `Handler.log_message` |
| C05 | `parse_body()` reads and rejects JSON arrays/scalars. | `do_POST()` pre-reads `request_bytes`. `parse_body()` calls `json.loads()` without imposing an object-only shape; endpoint `fields()` later rejects inappropriate shapes. | `Handler.do_POST`, `Handler.parse_body`, `fields` |
| C06 | All POST media are JSON; size behavior is unknown. | Photo/audio paths require multipart form data; ordinary paths require JSON. Declared bodies over `LIMIT` (2 MiB) receive `413`. File parts become dictionaries of `filename`, `content_type`, `data`. | `Handler.parse_body`, `LIMIT` |
| C07 | Missing approval might raise `PermissionError`; validation might raise `ValueError` directly. | Protocol validation raises `RequestError` with its HTTP status. Date parsing can still raise `ValueError`; `do_POST()` translates selected Python exceptions to `400`. | `RequestError`, `Handler.dispatch`, `Handler.do_POST` |
| C08 | Failed authorization maps to `403`. | Missing/invalid fixed sandbox bearer is `401`; `X-Sandbox-Failure: 403` is an explicitly simulated provider-permission failure. | `Handler.do_POST`, `TOKEN` |
| C09 | Execution might apply a real Calendar change; retry behavior is unknown. | No external provider call occurs. A first confirmed execution increments `provider_calls` and appends history; a succeeded retry does neither again. | `Handler.dispatch`, `SandboxServer.__init__` |
| C10 | Constructor simply forwards arbitrary keyword arguments. | It supplies `directory=str(ROOT / "public")`; a caller-supplied `directory` conflicts. | `Handler.__init__`, `ROOT` |

## Evidence and limits

On 2026-10-12, an offline audit used inert `Handler.__new__` instances, in-memory
streams, mocks, and isolated server state. It observed three raw-schema `400`
rejections, the real envelope keys, JSON-array acceptance by `parse_body`, no
stdout/stderr from `log_message`, a successful corrected Calendar flow with one
write/history record after a retry, and `401` for a missing bearer. These probes
did not contact an external service or assert production behavior. The source
symbols above are stable citations; line numbers are deliberately not used.

No naturally generated ghost method was found in the preserved draft. Its
seven method names match the supplied API. The incompatible fields are observed
**draft hypotheses about an API contract**, not unqualified factual claims and
not nonexistent methods. Any separately seeded `Handler.cancel_action` control
is artificial and must not be counted as a naturally discovered model error.

The source-reviewed corrections improve this local documentation. The lab's
independent manual-versus-GPT-4/Claude procedure remains unperformed; this audit
does not conceal that provenance gap.
